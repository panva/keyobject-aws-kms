tiny-aws-kms-openssl-provider -- what is left
=============================================

Scope: an OpenSSL provider for using AWS KMS asymmetric keys from Node.js.
Not a general-purpose KMS provider; the supported surface is what Node reaches.

Signing is DONE for every key spec in scope and verified against real AWS KMS.
398 aws-backend tests, 374 offline, 219 C unit checks, clean against OpenSSL
3.0.21 / 3.5.7 / 3.6.3 / 4.0.1, on macOS-arm64 and Linux-arm64.

CI is live as of 2026-08-05, on real runners rather than only locally: ci.yml
over SIX targets -- darwin-{arm64,x64}, linux-{x64,arm64}, linuxmusl-{x64,arm64}
-- both backends; the real-kms job against the actual service (208 passing, 0 keys
left billable); and release artifacts built, uploaded, and verified by
downloading one and running it. The six-target matrix is pushed but not yet
observed green on a runner: four of the six legs had never executed before, and
the musl pair is verified locally against a real Alpine container instead.

Requires Node >= 26.7.0, where the OSSL_STORE loader shipped; the floor lives in
.node-version and is read by both workflows.

THIS FILE IS ONLY WHAT IS LEFT. Why things are the way they are -- decisions,
measurements, dead ends already paid for -- is in docs/journal.md. The three-tier
distribution plan is in docs/distribution.md. Each item below stands on its own;
nothing here requires reading anything else first.

[x] Q2. DECIDED 2026-08-05: v1 SHIPS register(). src/napi.c is landed, the
        `./register` subpath is exported, and 15 npm checks run on every CI leg.

        The cnf route remains the DEFAULT in the docs, and the one to recommend
        to anyone running under --permission -- see the grant comparison below.
        register() is the ergonomic path: `import 'pkg/register'`, no flag, no
        cnf, and a failed registration throws instead of failing silently.

        The evidence behind the decision, kept because it is what makes the
        --permission guidance credible rather than assertion:

        MEASURED, macOS arm64 and linux (both backends):
          one artifact exports exactly OSSL_provider_init and
            napi_register_module_v1 -- no second binary, no second release matrix
          cost: 448 bytes (210384 -> 210832)
          the ONE napi reference is WEAK on both platforms ("weak external" on
            Darwin, `w` on ELF), so the module still loads in hosts with no napi
            at all -- the openssl CLI reports it active, and that CLI uses
            RTLD_NOW, which was the specific thing recorded as INFERRED
          as an addon: process.dlopen registers the provider in-process with NO
            cnf and NO CLI flag, createPrivateKey reaches our loader, and
            crypto.generateKeyPair still works, so the ?provider!=awskms guard
            holds when set this way
          aws backend on linux -- hidden visibility, static archives,
            --exclude-libs,ALL, the version script -- builds and behaves
            identically, with 0 libcrypto in NEEDED

        THE COST, WHICH IS THE WHOLE DECISION. Minimum grants under --permission:
          cnf route                   --allow-openssl-store
          addon, direct module path   --allow-addons --allow-openssl-store
          addon via npm (REAL path)   --allow-addons --allow-openssl-store
                                      --allow-fs-read
        The npm route needs the third because import() resolves through
        node_modules. I briefly "corrected" the plan to two grants; that was
        measured with a direct path and is not the route a user takes.

        It is QUALITATIVE, not just 1-vs-3: --allow-openssl-store is a scoped
        capability, --allow-addons is arbitrary native code. Buying one dlopen
        with the whole permission model is a bad trade for anyone who cares about
        --permission, and those people are precisely this provider's audience.

        WHAT IT BUYS: `import 'pkg/register'` with no flag at all, and traps
        (a) (b) (c) eliminated rather than documented -- a failed registration
        THROWS out of require() instead of failing silently at first use.

        node:ffi IS NOT A REPLACEMENT -- settled by measurement 2026-08-05,
        against STOCK 26.7.0 rather than the dev build. It was a live candidate
        when the addon was believed to cost a SECOND native binary per platform.
        That binary does not exist, so ffi's one advantage is gone and nothing
        replaces it:

                          cnf route      napi addon        node:ffi
          extra artifact  none           none (448 B)      none
          CLI flag        --openssl-     NONE              --experimental-ffi
                          config
          --permission    1: openssl-    3: fs-read,       3: fs-read, ffi,
                          store            addons,           openssl-store
                                           openssl-store
          stability       stable         stable (N-API)    EXPERIMENTAL (1)

        Measured: node:ffi is compiled into stock 26.7.0 and the ffi route does
        register the provider there (ERR_OSSL_AWSKMS_INVALID_URI, i.e. our loader
        answered). --experimental-ffi is still required, though it is on the
        NODE_OPTIONS allowlist. Minimum grants are identical to the addon's --
        three either way, differing only in --allow-ffi vs --allow-addons.

        THE DECISIVE POINT IS THE FLAG. The whole reason to register in-process is
        `import 'pkg/register'` with nothing on the command line. --experimental-
        ffi gives that up, and once a flag is being passed anyway --openssl-config
        is strictly better: one scoped grant instead of three, and nothing
        experimental in a signing path. So ffi is dominated on every axis it was
        supposed to win.

        ASSERTED, not merely present: check-load.sh requires exports to be
        EXACTLY {OSSL_provider_init, napi_register_module_v1} and every napi
        reference to be WEAK -- the latter being the only automated thing stopping
        a future contributor from adding a plain napi_* call and silently ending
        the provider's life in every host that is not node.

        WHAT THE DOCS MUST SAY, since shipping both routes means users choose:
        register() needs --allow-addons + --allow-openssl-store + --allow-fs-read;
        the cnf route needs --allow-openssl-store alone. That is qualitative, not
        3-vs-1: --allow-openssl-store is a scoped capability, --allow-addons is
        arbitrary native code. Under --permission, prefer opensslConfigPath().
        The register() docstring in npm/core/index.js already says so.

        That also closed a real gap: the npm core package listed darwin-x64 in

        have installed cleanly and hit "not installed" at first use.

        AND A TRAP FOUND WHILE ADDING IT: the archive-naming step mapped
        `macos-*` to darwin-arm64 unconditionally, which would have labelled the
        Intel leg's x86_64 bytes as arm64. Names now come from
        `node -p "process.platform + '-' + process.arch"` -- the exact expression
        the npm package uses to look the satellite up, so the artifact name and
        the lookup cannot drift and there is no table to forget.

        MUSL IS IN, DONE 2026-08-05. Six targets: darwin-{arm64,x64},
        linux-{x64,arm64}, linuxmusl-{x64,arm64}. Built by the build-musl job
        and verified on arm64 locally against a real Alpine container, BOTH
        backends -- 374/374 stub, 398/398 aws, check-load clean (no libcrypto,
        full symbol audit against a musl node), archive staged, unpacked
        elsewhere and re-verified, all 16 npm checks.

        The aws backend on musl was the last unverified combination and the one
        that ships; a passing stub build has never implied a passing aws build
        on any other platform either.

        "UNOFFICIAL BUILDS" TURNED OUT TO BE A NON-ISSUE, and an earlier note
        here saying the README should flag linuxmusl-* as resting on lesser
        footing was wrong and is withdrawn. nodejs.org/dist has no musl builds
        at all, so the floor comes from nodejs/unofficial-builds. Measured
        rather than assumed: the OpenSSL symbols exported by that build were
        compared one by one against the node:26-alpine image's own node --
        4648 each, ZERO in either direction, across two different node versions
        (26.7.0 vs 26.6.0). Since binding undefined OpenSSL symbols to the host
        is the entire mechanism this provider rests on, that surface is the only
        thing that matters and the two are interchangeable. Node classifying
        musl "Experimental" is a statement about Alpine generally, not about
        this provider, and does not belong in our README.

        THREE TRAPS FOUND WHILE ADDING IT, all silent:

        (a) THE CI MATRIX SILENTLY COLLAPSED TO ONE JOB. The platforms were
            listed under `include:`, and an include entry whose keys are ALL
            absent from the base matrix does not create a combination -- it is
            merged into the existing ones. `node-version` and `backend` each
            resolve to one value on a push, so there was exactly ONE
            combination; all six platform entries merged into it, each
            overwriting the last, and the matrix produced a single job carrying
            the LAST entry's values. Five of six legs never ran and nothing
            reported anything. Fixed by making the platform a real
            object-valued key, which cross-multiplies. This is why the failure
            surfaced as an arm64-Alpine error: the surviving entry happened to
            be the arm64 Alpine one.

        (b) `container: node:26-alpine` CANNOT WORK ON ARM64. The runner
            injects its own node to execute JavaScript actions and refuses
            outright: "JavaScript Actions in Alpine containers are only
            supported on x64 Linux runners." So actions/checkout dies before
            any step of ours. The musl legs now drive the container with
            `docker run` from an ordinary glibc runner instead -- checkout,
            cache and upload-artifact stay outside, only the build and tests go
            in. Identical on both architectures, and it removed an `if:` from
            nearly every step of the main build job.

        (c) THE ARCHIVE NAME WOULD HAVE COLLIDED. Staging derives the target
            from `process.platform + '-' + process.arch`, but node reports plain
            "linux" under musl too -- so a musl leg would have produced
            `awskms-linux-x64`, the same name as the glibc artifact, shipping
            musl bytes under a glibc key. The musl job hardcodes
            `linuxmusl-<arch>` (it only ever runs on musl) and the glibc job now
            ASSERTS glibcVersionRuntime is present rather than trusting it.

        WIN32 IS NOT A SUPPORT DECISION, IT IS BLOCKED. Read node's build config
        rather than measured -- there is no Windows machine here -- but the
        mechanism is unambiguous:

        The whole design is "compile against headers, link nothing, bind to the
        host at dlopen". On POSIX that works because of ONE line, common.gypi:581
        'ldflags': ['-rdynamic'], which exports every symbol from node -- measured
        earlier as the complete libcrypto ABI, 8880/8880.

        PE/COFF has no flat namespace and no dynamic_lookup: a DLL's imports bind
        to a NAMED DLL in its import table. Stock node.exe links OpenSSL
        statically and does NOT export it -- there is no .def and no
        __declspec(dllexport) for it, and node.gyp:643's MapExports is
        /MAPINFO:EXPORTS, a diagnostic map file, not exports. Addons link
        node.lib, which carries the N-API surface, not libcrypto. So there is
        nothing to import the OpenSSL ABI FROM.

        Three routes, all bad:
          upstream node exports the OpenSSL ABI on Windows -- not a change in
            this repo, and it means enumerating thousands of symbols in a .def
          resolve every OpenSSL call via GetProcAddress at runtime -- routing
            every call through a function-pointer table, a redesign rather than
            a port
          link a separate libcrypto.dll -- the exact second-OpenSSL catastrophe
            the design exists to prevent
        Secondary: weak_import/weak have no MSVC equivalent, so the weak
        napi_throw_error reference does not port either. Minor by comparison.

        PRECISE CLAIM: not possible for STOCK node.exe. A Windows node built
        --shared-openssl would work, since there would be a real libcrypto.dll to
        import from -- but that is not what anyone downloads.

        SETUP: a stand-in "user's existing config" that activates the legacy
        provider, so md4 is the observable (unavailable by default,

          their config alone            md4 WORKS
          ours alone                    md4 GONE, awskms working
          theirs + .include ours        md4 works, AWSKMS NEVER LOADS
          ours + .include theirs        awskms works, MD4 GONE

        TWO FINDINGS:
        1. Replacement IS wholesale, as suspected. Setting --openssl-config or
           OPENSSL_CONF loses whatever the host config was doing -- FIPS policy,
           a corporate CA, a pkcs11 provider section.
        2. `.include` DOES NOT COMPOSE, which is the part worth knowing. The
           top-level nodejs_conf key names ONE section and the FIRST assignment
           wins; the other file's providers are then silently never activated.
           So the "ship a cnf that .includes the system one" idea does not work
           and must not be documented -- it would produce a config that looks
           right and silently drops half of itself.

        CONSEQUENCE: the shipped cnf carries no .include. The docs must tell
        people to MERGE -- one file, one providers section listing both -- and
        that is the only arrangement measured to work.

        KNOWN DIAGNOSTIC GAP, worth fixing if this bites anyone: in the
        theirs-first case the doctor inspected the file named by
        --openssl-config, found it entirely well-formed, and reported "ok module
        exists" -- while a DIFFERENT config was actually in effect. It has no way
        to see that the winning nodejs_conf came from somewhere else.

          1. apply the trust policy by re-running the bootstrap. It is idempotent
             -- an existing role is updated in place, not recreated -- and creates
             no keys, so it costs nothing:
               node scripts/real-kms-bootstrap.mjs --profile <admin> \
                 --github-repo ORG/tiny-aws-kms-openssl-provider [--dry-run]
             --github-repo IS NOT OPTIONAL. The OIDC statement is only emitted
             when it is set, and update-assume-role-policy REPLACES the document
             rather than merging, so omitting it silently strips GitHub's access
             and CI stops being able to assume the role.
             Read the result back with `aws iam get-role` rather than assuming.
          2. create the label, or the gate can never be satisfied:
               gh label create real-kms \
                 --description "run the real-KMS suite on this PR (spends money)" \
                 --color B60205

        WHAT THIS BUYS AND WHAT IT COSTS. A pull_request subject carries no branch
        and no label, so AWS cannot distinguish an intended PR run from any PR job
        in the repository -- the whole event type is allowed or none of it. The
        label gate lives ONLY in the workflow file. A job running PR-authored code
        can mint its own OIDC token (id-token:write is sufficient) and assume a
        role that creates and deletes KMS keys. Assuming the role and then
        clearing the AWS_* vars before running that code is NOT a mitigation.
        Fork PRs remain excluded independently of all this, because a fork gets no
        OIDC token at all on a pull_request event.

        If that trade is ever revisited, the structural fix is an Environment:
        it rewrites the subject to repo:ORG/REPO:environment:NAME, letting a
        separate sign-only role bind to exactly that subject while the admin role
        stays unreachable from any job running PR code.

        Unchanged and still worth a look someday: the StringLike has a wildcard in
        the MIDDLE of the subject, so an environment named "x:ref:refs/heads/main"
        would produce a matching subject. Left alone deliberately -- the wildcard
        absorbs an immutable-subject suffix whose exact shape is documented as
        unverified against a live token, and breaking a working deployment on an
        unverified assumption is the worse trade.

[ ] B4. THE SHIPPED ARTIFACT CANNOT LOAD ON AN OPENSSL 3.0 HOST, and every CI
        job says green. Found 2026-08-06 while scoping the runtime OpenSSL
        matrix. This is the same shape as B1: a property verified one way
        (it compiles) recorded as a property it is not (it works).

        MEASURED. Built against homebrew 3.6.3 headers, the stub module's
        undefined set includes EVP_PKEY_sign_message_init; the shipping aws
        build additionally needs EVP_MD_CTX_get_size_ex. Checked against a real
        OpenSSL 3.0.20 libcrypto (debian:12, nm -D --defined-only):

          MISSING  EVP_PKEY_sign_message_init
          MISSING  EVP_MD_CTX_get_size_ex
          PRESENT  OPENSSL_strcasecmp      <- controls, proving the check works
          PRESENT  EVP_PKEY_sign_init

        Missing symbols make dlopen FAIL OUTRIGHT -- "symbol not found in flat
        namespace" -- not fail later at first use. So on such a host the
        provider does not load at all.

        WHY CI NEVER SAW IT. check-openssl-matrix.sh compiles against 3.0.21 /
        3.5.7 / 4.0.1 headers and greps for "Built target awskms". Compilation
        is not the failing axis. Nothing ever takes a module built against NEW
        headers and resolves it against an OLD libcrypto -- which is the only
        way this appears.

        THE AWS CASE IS A HEADER MACRO, which is why it survived review: s2n
        calls EVP_MD_CTX_size, which expands to EVP_MD_get_size(...) under 3.0
        headers but to the 3.4+ FUNCTION EVP_MD_CTX_get_size_ex under 3.6
        headers. Identical vendored source, different undefined symbol,
        determined entirely by the build host's headers.

        FIX, two parts. DECIDED 2026-08-06: floor is 3.0, on the strength of
        node testing shared-3.0.21 as a required CI leg -- that population is
        real, and a 3.5-built artifact cannot load there at all.

          1. Build release artifacts against the OLDEST supported headers
             rather than whatever the runner happens to have.
             VERIFIED LOCALLY 2026-08-06, stub backend, macOS arm64:
               built against 3.0.21     -> 68 OpenSSL symbols, all within 3.0
               (against 3.6.3 it was 71, three of them unavailable on 3.0)
               check-load against the 3.6.3 CLI + node 26.7.0 -> all ok
               full suite on node 26.7.0 (bundled 3.5.7)     -> 289/289, 0 fail
             So compile-old-run-new holds. STILL WIRING: the build job needs a
             3.0 prefix on every platform, and the AWS backend has not been
             rebuilt against 3.0 -- only the stub has.

          2. scripts/check-symbol-floor.sh (NEW) -- nm -u the module and diff
             against the lowest supported libcrypto's exports. No node, no
             runtime host, milliseconds. PROVEN to catch both instances:
               stub built vs 3.6.3 headers -> FAIL EVP_PKEY_sign_message_init
               shipped aws artifact        -> FAIL EVP_MD_CTX_get_size_ex
               3.0-built stub              -> ok        (control)
               stub vs the 3.6.3 it was built against -> ok  (control)
             Its real assertion is not "we compiled against 3.0" but "the build
             actually USED those headers rather than whatever the runner had",
             which is the mistake that produced B4 in the first place.

             The symbol-extraction rules now live in scripts/lib-symbols.sh,
             sourced by BOTH this and check-load.sh. Two copies of "which
             prefixes are OpenSSL" and "weak undefined symbols are not
             requirements" would have drifted. check-load.sh re-verified after
             the refactor: same 71 symbols, all checks pass.

        STILL UNVERIFIED: whether a 3.0-BUILT provider still drives ML-DSA on a
        3.5+ host. The run above could not answer it -- the stub drops those
        suites under 3.0 headers, so ML-DSA was never exercised. It needs the
        aws backend built against 3.0 and pointed at real KMS, or the runtime
        OpenSSL matrix. Do not claim ML-DSA works on a 3.0-built artifact until
        one of those has run.

        SCOPE. Stock nodejs.org builds bundle OpenSSL 3.5.7 (node 26), so they
        are unaffected. The exposure is --shared-openssl hosts pinned to 3.0 --
        RHEL 9, Ubuntu 22.04, Debian 12. Note also OPENSSL_strcasecmp arrived in
        3.0.3 while Ubuntu 22.04 ships 3.0.2, so "3.0" is not one floor.
        Whatever the outcome, the >= 3.0 claim in the README is currently false
        for the binaries we publish and must either be made true or narrowed.
        Blocks: T4 (what the artifacts are built against), T1 (the claim).

        REAL-KMS FOLDED IN, DONE 2026-08-06. real-kms.yml is deleted; the job
        lives in ci.yml, and real-kms-label.yml takes the label back off.
        real-kms-reaper.yml stays -- it is the dead man's switch for a runner
        that dies before teardown, and folding the tests in makes it MORE
        necessary, not less.

        Four things had to be got right, three of which are only visible if you
        go looking:

          * THE GATE IS AN ALLOW-LIST. The natural phrasing carried over from
            real-kms.yml -- `github.event_name != 'pull_request' || (...)` --
            is TRUE FOR PUSH. real-kms.yml never ran on push; ci.yml runs on
            every push to main and on tags. Left inverted, every commit that
            landed would have spent money. The condition now enumerates the
            events that may spend.
          * TWO CADENCES, kept apart by github.event.schedule. real-kms.yml ran
            daily; ci.yml's cron is every 5 days (sized to GitHub's 7-day cache
            eviction). Folding without this would have silently stretched the
            real-KMS smoke pass from daily to 5-daily, and arming it off ci.yml's
            cron would have dragged the ~206 MB aws matrix along daily.
          * DISPATCH SPENDING IS OPT-IN. Dispatching ci.yml by hand is ordinary
            -- warming the SDK cache, running the aws backend before a release --
            and must not quietly cost money. A `real_kms` checkbox, default off.
          * CONCURRENCY. A label-triggered run gets its OWN workflow-level group
            with cancellation disabled, because cancelling a run that has already
            created keys is exactly what leaves them billing. The job also joins
            the reaper's cross-workflow `awskms-real-kms` group. Job-level
            concurrency accepts only `group` and `cancel-in-progress`, so
            `queue: max` cannot be carried over -- the loss is a lossy PENDING
            queue, never a cancelled RUNNING one, and only a running job holds
            keys.

        The label is armed by the LABELLING EVENT, not by the label being
        present. That is what makes it a true one-shot: a later `synchronize`
        cannot re-fire it, so safety does not depend on the remover winning a
        race. Removal exists only so the button can be pressed again.

        OPENSSL RUNTIME LANES DONE 2026-08-06, and far cheaper than first
        scoped. I had proposed building node --shared-openssl per version via
        node's own tools/nix/openssl-matrix.nix (~112 min a leg, or ~5 with
        node's prebuilt V8 from cachix). That answers a question nobody asked.
        What varies with the OpenSSL version is the module's SYMBOL BINDING and
        provider registration, and libcrypto is the loader, not node: OpenSSL's
        DSO layer dlopens with RTLD_NOW, so every undefined symbol must resolve
        at load or the load fails outright. The `openssl` CLI of a version is
        therefore a faithful host for the whole question -- and build-openssl.sh
        already installs one per version. No node build, no nix, no cachix.

        against the floor, not rebuilt per version -- and loads it into each of
        3.0 / 3.5 / 4.0. That crossing is precisely the gap B4 lived in:
        openssl-headers proves each header tree COMPILES, and every one of them
        did while the shipped artifact could not load on 3.0.
