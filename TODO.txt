tiny-aws-kms-openssl-provider -- what is left
=============================================

Scope: an OpenSSL provider for using AWS KMS asymmetric keys from Node.js.
Not a general-purpose KMS provider; the supported surface is what Node reaches.

Signing is DONE for every key spec in scope and verified against real AWS KMS.
398 aws-backend tests, 374 offline, 219 C unit checks, clean against OpenSSL
3.0.21 / 3.5.7 / 3.6.3 / 4.0.1, on macOS-arm64 and Linux-arm64.

CI is live and green as of 2026-08-05, on real runners rather than only locally:
ci.yml across ubuntu-latest / ubuntu-24.04-arm / macos-latest, both backends, all
11 jobs; real-kms.yml against the actual service (208 passing, 0 keys left
billable); and three release artifacts built, uploaded, and verified by
downloading one and running it. Requires Node >= 26.7.0, which published that
day; the floor lives in .node-version and is read by both workflows.

THIS FILE IS ONLY WHAT IS LEFT. Why things are the way they are -- decisions,
measurements, dead ends already paid for -- is in docs/journal.md. The three-tier
distribution plan is in docs/distribution.md. Each item below stands on its own;
nothing here requires reading anything else first.

Requires Node >= 26.7.0, where the OSSL_STORE loader shipped.

[ ] Q1. npm scope and package names.
        The plan assumes a core package plus one per architecture, following
        esbuild. Placeholders in use: `awskms-openssl-provider` and
        `@awskms-openssl-provider/<platform>-<arch>`. Nothing can be published,
        and no README install section can be written, until these are real.
        Blocks: T4, T5, and the install half of T1.

[ ] Q2. Does v1 ship in-process registration at all?
        A single .so can be both the provider and its own N-API addon (measured;
        costs 448 bytes), so `import 'pkg/register'` needs no second artifact and
        no CLI flag. But under --permission it additionally needs --allow-addons,
        which is arbitrary native code, where the config-file route needs only
        --allow-openssl-store, a scoped capability. Shipping only the cnf route
        in v1 and adding register() later is defensible.
        Blocks: the shape of T5, and whether src/napi.c lands at all.

[ ] Q3. musl (and win32) in or out for v1.
        Currently out. Four release artifacts if out, six if musl is in. musl is
        a genuinely different artifact -- different libc ABI, no symbol
        versioning, so none of the glibc analysis carries over -- and has no
        GitHub-hosted runner. win32 needs different N-API code entirely.
        This is a support commitment, not a technical question.
        Blocks: the matrix in T4.

[ ] Q4. Linux glibc floor.
        Recommendation is 2.34, by building in almalinux:9, which covers RHEL 9,
        Amazon Linux 2023 including Lambda, Ubuntu 22.04+ and Debian 12+. Going
        lower buys only distributions that are EOL or nearly so, at the cost of
        an OpenSSL-3.0-headers problem. Confirm or override.
        Blocks: T4.

[x] Q5. ANSWERED BY MEASUREMENT 2026-08-05, not by decision. It was filed as a
        judgement call and was not one -- the question was empirical.

        SETUP: a stand-in "user's existing config" that activates the legacy
        provider, so md4 is the observable (unavailable by default,
        ERR_OSSL_EVP_UNSUPPORTED).

          their config alone            md4 WORKS
          ours alone                    md4 GONE, awskms working
          theirs + .include ours        md4 works, AWSKMS NEVER LOADS
          ours + .include theirs        awskms works, MD4 GONE
          genuinely merged, one
            providers section           BOTH work

        TWO FINDINGS:
        1. Replacement IS wholesale, as suspected. Setting --openssl-config or
           OPENSSL_CONF loses whatever the host config was doing -- FIPS policy,
           a corporate CA, a pkcs11 provider section.
        2. `.include` DOES NOT COMPOSE, which is the part worth knowing. The
           top-level nodejs_conf key names ONE section and the FIRST assignment
           wins; the other file's providers are then silently never activated.
           So the "ship a cnf that .includes the system one" idea does not work
           and must not be documented -- it would produce a config that looks
           right and silently drops half of itself.

        CONSEQUENCE: the shipped cnf carries no .include. The docs must tell
        people to MERGE -- one file, one providers section listing both -- and
        that is the only arrangement measured to work.

        KNOWN DIAGNOSTIC GAP, worth fixing if this bites anyone: in the
        theirs-first case the doctor inspected the file named by
        --openssl-config, found it entirely well-formed, and reported "ok module
        exists" -- while a DIFFERENT config was actually in effect. It has no way
        to see that the winning nodejs_conf came from somewhere else.

        CAUSE: the subject was GUESSED. Repositories created after 2026-07-15
        emit IMMUTABLE subjects carrying owner and repo IDs:

        exactly the case the docs had flagged as "unverified against a live
        token" -- now verified, in the failing direction.

        FIX: do not guess. GitHub reports the exact prefix:
          gh api repos/OWNER/REPO/actions/oidc/customization/sub \
            --jq .sub_claim_prefix
        real-kms-bootstrap.mjs now reads it and uses it verbatim, so the
        condition is StringEquals with NO wildcard at all.

        CORRECTION TO AN EARLIER NOTE HERE: renaming the repo does NOT break the

        the NAME-based form that would silently stop matching.

        Already written:
          scripts/real-kms-bootstrap.mjs   emits both subjects

        STILL TO DO, both only the account/repo owner can:
          1. apply the trust policy by re-running the bootstrap. It is idempotent
             -- an existing role is updated in place, not recreated -- and creates
             no keys, so it costs nothing:
               node scripts/real-kms-bootstrap.mjs --profile <admin> \
                 --github-repo ORG/tiny-aws-kms-openssl-provider [--dry-run]
             --github-repo IS NOT OPTIONAL. The OIDC statement is only emitted
             when it is set, and update-assume-role-policy REPLACES the document
             rather than merging, so omitting it silently strips GitHub's access
             and CI stops being able to assume the role.
             Read the result back with `aws iam get-role` rather than assuming.
          2. create the label, or the gate can never be satisfied:
               gh label create real-kms \
                 --description "run the real-KMS suite on this PR (spends money)" \
                 --color B60205

        WHAT THIS BUYS AND WHAT IT COSTS. A pull_request subject carries no branch
        and no label, so AWS cannot distinguish an intended PR run from any PR job
        in the repository -- the whole event type is allowed or none of it. The
        label gate lives ONLY in the workflow file. A job running PR-authored code
        can mint its own OIDC token (id-token:write is sufficient) and assume a
        role that creates and deletes KMS keys. Assuming the role and then
        clearing the AWS_* vars before running that code is NOT a mitigation.
        Fork PRs remain excluded independently of all this, because a fork gets no
        OIDC token at all on a pull_request event.

        If that trade is ever revisited, the structural fix is an Environment:
        it rewrites the subject to repo:ORG/REPO:environment:NAME, letting a
        separate sign-only role bind to exactly that subject while the admin role
        stays unreachable from any job running PR code.

        Unchanged and still worth a look someday: the StringLike has a wildcard in
        the MIDDLE of the subject, so an environment named "x:ref:refs/heads/main"
        would produce a matching subject. Left alone deliberately -- the wildcard
        absorbs an immutable-subject suffix whose exact shape is documented as
        unverified against a live token, and breaking a working deployment on an
        unverified assumption is the worse trade.

        Add:
          - the four ways a provider install fails SILENTLY. They are commented
            in cmake/awskms.cnf.in but appear nowhere a user will look:
              (a) a failed provider load produces no output at all -- node starts
                  fine and fails at the first createPrivateKey
              (b) omitting `default = default_sect` aborts node at startup with

                  dlopen failure that node hides

            wrong. It costs no network call, no credentials and nothing billable,
            so it is safe to recommend unconditionally.
          - the permission-model posture, which is better than the README
            currently implies and needs no code change: load every key, then
            process.permission.drop('openssl.store') and drop('worker'). After
            that a compromise cannot load new KMS keys, while already-loaded keys
            keep signing. Two silent traps to name: the scope is "openssl.store"
            with a DOT while the CLI flag is --allow-openssl-store, and dropping
            an unknown scope is a no-op that has() then reports as success; and
            drops are per-thread, so a new Worker starts from the original CLI
            grants unless 'worker' is dropped too.

        TWO BUGS IN awskms-doctor.mjs THAT ONLY THE TARBALL PATH EXPOSED, both
        fixed, both mine:
          The main-module guard compared import.meta.url against argv[1]. The ESM
            loader resolves import.meta.url through SYMLINKS and argv[1] is left
            as typed, so unpacking under /tmp on macOS -- where /tmp is a symlink
            to /private/tmp -- made the guard false. The doctor printed NOTHING
            and exited 0: a health check whose entire purpose is eliminating
            silent failures, failing silently and reporting success. Now
            import.meta.main, which is symlink-correct.

            sentinel that turned out to be literal NUL bytes, making the file
            "binary" to grep and git diff -- which is how an unused import stayed
            invisible. Now returns { expanded, unset } and the file is ASCII.

[ ] M3. Ed25519 stays capped at 4096 bytes and cannot be lifted. PureEdDSA needs
        the whole message and KMS caps Message at 4096. ED25519_PH_SHA_512 does
        not help: KMS re-applies the SHA-512 prehash, so feeding it SHA-512(M)
        signs SHA-512(SHA-512(M)), which no standard verifier computes.
        Documented in the README; not a bug to fix.

    --  SM2 is out of scope by decision (China partitions only, and OpenSSL's
        SM2 digest signing is not equivalent to a prehashed sign).
